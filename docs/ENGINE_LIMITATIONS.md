# Engine limitations

- TER v5 has one height per X/Z. Overhangs, caves and negative volumes do not fit in one terrain layer. A future prop or mesh placement workflow requires its own model, collision, and mission validation.
- The native TER sample interval is 2 m in the reviewed format. The 8 m TRN setting is an independent parameter. Heights are floats in the file. VRV observed non-granularity-aligned values in-game, so the editor's snapping is a controlled authoring choice. The ±32,000 step editing bound is conservative and does not claim an engine maximum.
- The preview intentionally renders elevation. Its colors and tessellation do not reconstruct the complete BZCC material stack. Near the camera and brush cursor (`<= 160` samples), the 3D view renders at native 2 m terrain sample resolution (`step = 1`) with boundary seam snapping to coarser mid (`4 m`) and distant (`8 m`) chunks; brush sampling and export retain 2 m heights across the entire map.
- The layout registry (`app/formats/bzn_layouts.gd`) gates the BZN codecs and Playtest by capability. The launcher checks the path table, trailer, object records and native package before admitting 1192 or 1196. The 1196 route requires the VRV adapter, including in `-ValidateOnly`. Binary 1197 is available for path editing, and text 1200 for layout recognition. Template-cloned object insertions and unreferenced object removals on verified 1192/1196 layouts now export immediately before the 640-byte `groupTargets` mission boundary with unique `kind=8` pointer IDs and reach MISSION / RUN on 2.0.185 with zero `SAVEGAME CORRUPT` lines (the earlier offset-20976 failure came from inserting after `groupTargets` + `dllName` and reusing template pointer IDs). Synthesizing arbitrary new object classes not yet present in the map still lacks per-class binary serializers and remains pending; pointer-referenced object removals are refused to avoid dangling mission links. Position and orientation edits remain supported by MISSION / RUN evidence.
- Missing mod assets, omitted packed companions, Steam availability and mission DLL dependencies can prevent loading after a valid TER parse. The package loader currently expects same-stem BZN/TRN/INF/TER on disk. Some stock packages store those files in different search roots or archives.
- VRV's 2.0.206.10 comparison identifies local fog controls and several weather/texture-rate settings that require a newer executable. Its 2.0.185 port covers only a subset. Newer version support remains experimental.
- Native `.SKY` editing on 2.0.185 is scoped strictly to the verified `sky-v1-7068` layout (296/304 scanned BZCC/VRV `.SKY` files) and the 8 runtime-verified `1YKS` float groups (`fogColor`, `fogStart < fogEnd`, `visibilityRange`, `sunPeriod`, `sunAngle`, `sunColor`, `ambientColor`). All other `.SKY` chunks (`EMOD` dome mesh, `NIAR` rain, `TLPS` splat, ` GOF` multi-layer fog, `RRIM`, `RATS` stars, `TRPS` sprites, `RTAW`, `TLOB` lightning, `_VNE`, `CVNE`) remain read-only and are preserved byte-for-byte. Variant/unknown `.SKY` layouts (such as 7,044-byte datapak files without `CVNE`, 7,100-byte `SBPS`/`DGOF` files, duplicate-tag or reordered chunks) stay strictly `READABLE_SKY` read-only without blocking terrain editing. The 3D viewport environment toggle is an `Approximate Editor Preview` rather than a guaranteed 1:1 D3D9 engine renderer match, and VRV's full weather/2.0.206.10 local-fog controls remain partial/pending. Water remains independently supported via WAT v5.
- Playtest runs a native game process with a private resource configuration and separate profile. It exposes launch/exit status. Steam remains the actual client, and BZCC can write session logs to its shared Documents log directory. Runtime hot reload and external three-way merge are pending.
- The node evaluator covers a circular region up to 256 m radius. Its material outputs cover vertex RGB and the base tile lane. Tile evaluation samples each 16 × 16 block at its center.
